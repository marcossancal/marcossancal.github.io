Web scraping: o que é, quando faz sentido usar e quando evitar

Marcos Sanches · 10 de agosto de 2026 · 7 min de leitura
Web Scraping · Coleta Automática · Python · Dados

Web scraping é um daqueles termos que provoca reações opostas dependendo de quem você pergunta. Para alguns, é sinônimo de coisa ilegal ou de spam. Para outros, é uma ferramenta técnica como qualquer outra — neutra, poderosa e com usos legítimos bem estabelecidos.

A realidade está no meio. Scraping pode resolver problemas reais de negócio de forma elegante — e pode também ser usado de formas problemáticas. Este artigo trata do uso empresarial legítimo: o que é, em que situações resolve, o que você precisa saber antes de contratar alguém para fazer, e um case real de um sistema que construí para escritórios de advocacia.

O que é web scraping, sem complicar

Quando você abre um site no navegador, o navegador faz uma requisição ao servidor, recebe o HTML da página e renderiza o conteúdo visualmente para você. Web scraping é basicamente isso — mas feito por um programa, não por um humano.

O script acessa a URL, recebe o HTML, identifica as partes que interessam (uma tabela de preços, uma lista de resultados, um conjunto de dados específicos) e extrai essas informações de forma estruturada — salvando em uma planilha, em um banco de dados ou em qualquer outro formato útil.

A diferença de usar uma API é que a API é uma porta que o dono do sistema abriu de propósito para que outros sistemas se comuniquem com ele. O scraping é uma forma de pegar o conteúdo que está visível na tela quando não existe essa porta — ou quando ela não está disponível para você.

Um case real: monitoramento de processos judiciais no eSAJ

O eSAJ é o sistema de consulta de processos do Tribunal de Justiça de São Paulo. Qualquer pessoa pode acessar pelo navegador e consultar o andamento de um processo pelo número — mas não existe API pública para fazer isso de forma automatizada.

Para um escritório de advocacia com dezenas ou centenas de processos ativos, acompanhar as movimentações de cada um manualmente é inviável. Advogados e assistentes gastam horas por semana entrando no sistema, copiando atualizações para planilhas, verificando prazos. É um trabalho puramente mecânico que só existe porque não tem automação.

O sistema que construí funciona assim:

  1. O escritório cadastra os números dos processos que quer monitorar
  2. O robô acessa o eSAJ periodicamente — de hora em hora, ou na frequência que o escritório definir
  3. Para cada processo, ele coleta o histórico de movimentações e compara com o que já estava registrado
  4. Quando detecta uma movimentação nova — uma decisão, uma intimação, um despacho — registra na planilha e envia uma notificação automática para o advogado responsável
  5. O resultado é uma planilha sempre atualizada com todos os processos, datas de movimentação, últimos andamentos e alertas de novidades

O que antes consumia horas de trabalho manual por semana passou a acontecer automaticamente, em segundo plano, sem que ninguém precisasse lembrar de checar.

Esse é o uso legítimo de scraping: substituir um processo manual repetitivo e sem valor intelectual por automação — coletando dados que são públicos, de um sistema que não oferece API alternativa, sem prejudicar a operação do sistema de origem.

Outros casos de uso empresarial que fazem sentido

O eSAJ é um exemplo, mas a mesma lógica se aplica em vários outros contextos:

  • Monitoramento de preços de concorrentes: acompanhar automaticamente como os preços dos seus concorrentes variam, sem precisar checar manualmente todos os dias.
  • Coleta de dados de portais públicos: informações de licitações, Diário Oficial, dados do governo, registros públicos — qualquer coisa que esteja disponível publicamente mas não tenha API.
  • Agregação de dados para análise: consolidar informações de múltiplas fontes em um único banco de dados para análise interna.
  • Geração de leads com dados públicos: coletar informações de negócios que estejam disponíveis publicamente — nome, endereço, segmento — de portais como Google Maps, portais de empresas ou listas públicas.
  • Automação de portais sem API: qualquer sistema legado, portal governamental ou ferramenta interna que não oferece integração programática mas precisa se comunicar com outros sistemas.

Limites que você precisa conhecer

Scraping não é território sem regras. Existem três limites principais que qualquer projeto responsável precisa respeitar:

LGPD e dados pessoais

A Lei Geral de Proteção de Dados protege informações de pessoas físicas identificáveis. Coletar, armazenar e usar dados pessoais sem base legal é problemático — mesmo que as informações sejam tecnicamente acessíveis. Se o projeto envolve coletar nomes, CPFs, e-mails, telefones ou qualquer outro dado pessoal, isso precisa ter uma finalidade legítima e documentada.

Termos de Serviço do site

Muitos sites proíbem scraping nos seus Termos de Serviço. Isso não é uma lei — é um contrato. Descumprir pode gerar bloqueio de IP, encerramento de conta ou, em casos extremos, ação civil. Vale sempre verificar o que os termos do site dizem sobre uso automatizado antes de começar qualquer projeto.

Impacto na operação do site

Um robô mal configurado pode fazer centenas de requisições por segundo e sobrecarregar o servidor do site que está sendo coletado. Isso, além de antiético, pode configurar crime. Qualquer scraper responsável respeita limites de taxa — número máximo de requisições por minuto — e opera de forma que não prejudique a disponibilidade do site para outros usuários.

A regra prática: dados públicos, sem dados pessoais sensíveis, coletados sem prejudicar a operação do site, para uma finalidade interna legítima — em geral é território seguro. Quando surgir dúvida, o caminho é consultar um advogado antes de desenvolver, não depois.

Quando scraping não é a resposta certa

Existem situações em que scraping parece a solução mas não é — e é importante identificar isso antes de investir no desenvolvimento:

  • Quando existe API disponível: se o sistema tem API, use a API. É mais estável, mais rápida e tecnicamente mais limpa. Scraping é a alternativa quando não existe outra saída.
  • Quando o site muda frequentemente: scraping depende da estrutura HTML da página. Se o site redesenha a interface constantemente, o robô quebra com frequência e exige manutenção contínua. Nesses casos o custo de manutenção pode superar o benefício.
  • Quando o dado é protegido por autenticação que você não tem: acessar sistemas que exigem login com credenciais que não são suas é invasão de sistema — crime previsto no artigo 154-A do Código Penal brasileiro.
  • Quando o volume é tão pequeno que fazer manualmente é mais rápido: se você precisa coletar 10 itens uma vez por mês, o desenvolvimento de um robô não compensa. Scraping faz sentido para volume, frequência ou complexidade que torna o processo manual inviável.

O que define a complexidade — e o custo — de um projeto de scraping

Nem todo projeto de scraping tem o mesmo esforço. O que mais impacta a complexidade:

  • O site usa JavaScript para carregar conteúdo? Sites estáticos são mais simples. Sites que carregam dados via JavaScript após a renderização precisam de um navegador headless (Playwright, Puppeteer) — mais lento e mais complexo.
  • Existe CAPTCHA? CAPTCHAs são barreiras específicas contra automação. Existem formas de contornar — serviços de resolução, técnicas de evasão — mas adicionam custo e fragilidade.
  • O site bloqueia por IP ou por padrão de comportamento? Requer rotação de proxies e simulação mais cuidadosa de comportamento humano.
  • Qual o volume e a frequência? Coletar 100 itens uma vez é diferente de coletar 10.000 itens a cada hora.
  • O dado precisa ser processado antes de salvar? Às vezes o que está na página precisa ser normalizado, calculado ou combinado com outras fontes antes de ser armazenado.

Com o site e os requisitos na mão, é possível dar uma estimativa precisa de prazo e custo. Sem isso, qualquer número é chute.

Perguntas frequentes

Não existe uma lei no Brasil que proíba web scraping de forma genérica. O que existe são limites: a LGPD protege dados pessoais, então coletar e armazenar dados de pessoas sem base legal é problemático. Os Termos de Serviço de cada site podem proibir scraping contratualmente. E forçar acesso a sistemas protegidos por autenticação sem autorização pode configurar crime. Dados públicos, sem dados pessoais, coletados sem prejudicar a operação do site — em geral, é território seguro.
Uma API é uma interface oficial que o dono do sistema disponibiliza para que outros sistemas se comuniquem com ele de forma estruturada e autorizada. O scraping é uma forma de extrair dados de um site ou sistema que não oferece API — você simula o comportamento de um navegador humano para coletar as informações. Quando existe API disponível, sempre prefira a API: é mais estável, mais rápida e tecnicamente mais limpa.
Na teoria, qualquer conteúdo que um navegador consegue renderizar pode ser coletado via scraping. Na prática, alguns sites dificultam ativamente: CAPTCHA, bloqueio por IP, rate limiting, conteúdo carregado via JavaScript que precisa de renderização, login obrigatório. Cada um desses obstáculos tem formas de contornar — mas adiciona complexidade e custo ao projeto. A viabilidade técnica depende do site específico.
Depende muito da complexidade do site de origem e do volume de dados. Um scraper simples para um site estático com estrutura previsível pode ser desenvolvido em horas. Um sistema que precisa lidar com JavaScript dinâmico, autenticação, CAPTCHA e múltiplas fontes pode levar semanas. Para uma estimativa precisa, preciso saber o site de origem, o volume esperado e com que frequência a coleta precisa rodar.

Precisa coletar dados de algum lugar automaticamente?

Me conta o contexto: de onde vêm os dados, o volume aproximado e o que você quer fazer com eles. Com isso já consigo avaliar se scraping é a abordagem certa e o que seria necessário para construir.
